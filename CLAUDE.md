# skipper-cd

Lightweight Docker Compose CD tool in Go. Receives Git push webhooks (Gitea/GitHub HMAC), keeps a local clone of the deploy repo, and redeploys only stacks whose tracked files changed (SHA-256 hashes persisted in `state.yaml`). Optionally runs `nixos-rebuild` first when nix files change.

## Commands

- Build: `go build ./...` (binary: `go build -o skipper ./cmd/skipper`)
- Test: `go test ./...` — fast, needs no docker/git; tests inject fake runners
- Verify before finishing any change:
  `go build ./... && go vet ./... && go test ./... && test -z "$(gofmt -l cmd internal)"`
  (the `test -z` wrapper is required — `gofmt -l` exits 0 even when files need formatting; the paths `cmd internal` keep `vendor/` out)
- Lint: `golangci-lint run ./...` (config in `.golangci.yml`; locally via `nix run nixpkgs#golangci-lint -- run ./...`). CI runs it plus `go test -race`.
- Nix: `nix build` / `nix develop`. After dependency changes run `go mod tidy && go mod vendor` — the flake uses `vendorHash = null`, so `vendor/` must stay committed and in sync.

## Packages

- `cmd/skipper` — entrypoint; single `-config` flag (default `/etc/skipper/skipper.yml`); wires the packages (wiring.go, layers.go), registers the HTTP routes (routes.go) and joins the background loops on shutdown (bgloops.go)
- `internal/config` — YAML config load and validation. Files are cut **by feature area, not by kind**: a section's shape, its defaults and the rules that make it usable live together (`stack.go`, `healthcheck.go`, `healthwatch.go`, `notifications.go`, `peers.go`, `selfheal.go`, `icons.go`; the flat top-level keys in `source.go` (repo, clone paths, sync triggers), `hostpaths.go` and `server.go` (listeners, logging, UI, health poll)), each as an `applyDefaults`/`validate` method, so adding a field, its default and its validation is one file. `Stack.applyDefaults` is the one place both `Load` and `LoadRepoStacks` fill a stack's defaults. `config.go` holds the `Config` struct, its effective-value methods and `Load`, which only sequences decode → `applyDefaults` → `validateConfig` → resolve; `validate.go` only orchestrates (`validateConfig`'s call order, `collectWarnings`). Put a new section in its own file rather than growing these two back. In stack-discovery mode `LoadRepoStacks` also validates each stack against its compose file (parse, rollout eligibility, env/watch existence) every sync
- `internal/compose` — minimal read-only `docker-compose.yml` parser (`File`/`Service` + `PublishesPorts`/`HasHealthcheck`/`HasContainerName`, and `ReadinessBudget` for the health gate's derived timeout); shared by `deploy` (image/build/rollout) and `config` (discovery validation) so there is one parser
- `internal/deploy` — CORE, files grouped by concern:
  - run: the `Deployer` and run-level orchestration (deploy.go), stack order and `depends_on` outcomes (order.go, ordering.go), the run-plan SSE snapshot (runplan.go), the stack set in discovery mode (discovery.go), entry-level config errors as state, not events (configerrors.go, ADR-0055), stacks leaving the set (removed.go), the `project_directory` fast-forward (projectdir.go, ADR-0060), the nixos phase (nixos_rebuild.go, nixos_change.go, ADR-0065)
  - per-stack apply: the pipeline (stackrun.go), change hashing (hash.go), image/pull logic (images.go, wraps `internal/compose`), build contexts pinned to the clone (buildcontext.go), env files (envfile.go), hooks and the running-hook snapshot (hooks.go, hookrun.go), the deploy health gate (healthcheck.go), zero-downtime rollout (rollout.go), rollback (rollback.go), held changes (held.go, ADR-0062), the converge to the recorded version when a revert releases a hold (holdrelease.go, ADR-0068), self-heal's corrective up of the recorded version — never a queued or held change (heal.go, ADR-0029 amendment 2026-11-06)
  - reporting: deploy-event emission + change context + repo-relative paths (events.go), env-file values masked in diffs (diffmask.go), per-service change attribution for display (attribution.go, ADR-0059), version deltas from what the containers actually run (runningimages.go), the failure cause condensed from a failed command's stderr tail (failurecause.go, ADR-0063), compose `--format json` reads (composejson.go), the compose invocation container logs reuse (logs.go)
  - state persistence (state.go); runner.go aliases `command.Runner`
- `internal/command` — `Runner` interface over os/exec; tests inject fakes through it. A failed `Run` or `Output` returns `*command.ExitError` carrying the last stderr lines (`StderrTail`)
- `internal/regularfile` — the one way to read a file a Git push controls: opens only a regular file (O_NONBLOCK so a FIFO cannot block, type checked on the descriptor), optional no-follow, capped reads. Used by hashing, env files, compose parsing and repo icons
- `internal/containerlogs` — UI-only live `docker compose logs` over SSE (`/api/container-logs`, ADR-0037); own `LogStreamer` seam so the deploy path's `Runner` stays run-to-completion
- `internal/git` — local clone management (clone, reset --hard, diff, file-at-commit) plus `Checkout`, the fast-forward-only view of a working copy skipper does *not* own (the `project_directory` tree, ADR-0060); also redacts credentials from remote URLs for logs
- `internal/repourl` — pure Git remote URL *forms*: derives the forge browse URL the UI links commit SHAs through (`WebURL`); imported by `config`, which must stay free of `git`
- `internal/webhook` — HMAC-verified push handler; responds 202 immediately, deploy runs in a goroutine
- `internal/nixos` — nixos-rebuild; must stay free of docker/state/metrics/events knowledge
- `internal/events` — SSE broadcaster + bounded persisted event history. A terminal outcome that merely repeats a stack's previous one (same status, same error; failure statuses only) collapses into it rather than taking a slot, carrying `repeat_count`/`first_seen`/`supersedes_id` (ADR-0056) — the same rule `internal/audit` applies per stack, so one failure loop can never evict a stack's real history
- `internal/metrics` — Prometheus metrics
- `internal/roster` — builds the Stacks-view inventory (discovered/host stack set + last audit outcome per stack) and owns the `stacks` SSE snapshot that wraps it (`State`/`BuildState`/`RepoRef` in state.go); pure (docs/dev/stack-roster-spec.md)
- `internal/imageref` — what an image reference says about its version: the reference split (name/tag/digest), the conservative same-shape tag parser (`ParseShape`/`NewerTag`) the update check matches with, and the update level between two references (`Compare`: digest/patch/minor/major/unclassifiable) the `rollback: patch_only` gate decides on (ADR-0074). Pure, no I/O
- `internal/registry` — minimal read-only Registry HTTP API v2 client (tags list + manifest-digest HEAD, docker-config credentials, challenge auth); exists solely for the update check (ADR-0054) and must never pull or push
- `internal/updatecheck` — read-only registry update check (ADR-0054): compares each stack's `running_images` against its registries (conservative same-shape tag matching + moved-digest detection), publishes a runtime-only snapshot that rides the `stacks` SSE state, and — only under the opt-in `update_check.notify: true` (default **false**, the UI is the surface) — fires one deduped notification per newly appearing update (dedup persisted in `update-check.yaml`). Never a deploy input — not hashed, not a pull input, no trigger
- `internal/peers` — multi-host read-data fan-in (ADR-0048, docs/dev/multi-host-spec.md): the primary polls each `peers:` instance's `/api/v1/snapshot` + `/api/v1/audit` (falling back to the legacy `/api/audit` only on 404 from an older peer), tags records by host, and exposes one merged `peers` state its own UI renders. Read-only; touches no deploy/state invariant. Wired in main under `ui_enabled` (`GET /api/peers`, the peer-diff proxy `GET /api/peers/{name}/events/{id}/diffs`, and the peer container-logs SSE proxy `GET /api/peers/{name}/container-logs/{stack}[/{service}]`)
- `internal/audit` — durable per-stack log of terminal deploy outcomes (compact metadata, no diffs), outliving the bounded event ring (ADR-0033)
- `internal/notify` — fire-and-forget outbound notifications on terminal deploy outcomes, health transitions and updates; never blocks the deploy path (ADR-0020)
- `internal/autosync` — effective autosync state per stack (config defaults + non-persistent UI overrides) and the paused-change queue (docs/dev/autosync-spec.md)
- `internal/reconcile` — periodic sync + deploy so a lost webhook cannot leave the host drifted (ADR-0028); drives an injected `Reconciler`
- `internal/health` — read-only runtime-health poller of skipper's own stacks, publishing per-stack snapshots (ADR-0027)
- `internal/selfheal` — corrective redeploy of opted-in stacks that stay degraded, fed by the health snapshots (debounce, cooldown, max attempts; ADR-0029)
- `internal/healthwatch` — per-service health transitions, bounded phase history and failed/recovered alerts from the same snapshot feed (ADR-0031)
- `internal/orphans` — classifies running compose projects the discovered stack set no longer accounts for (ADR-0036); the optional prune acts only on the orphaned class
- `internal/applink` — best-effort Traefik hostnames per stack from live container labels, for the Stacks-view app link (docs/dev/traefik-app-links-spec.md)
- `internal/icons` — resolves and disk-caches stack icons: repo override file, then slug override, then name match against an external icon set (docs/dev/service-icons-spec.md)
- `internal/logbuf` — bounded in-memory log ring with live fan-out behind `/api/logs`; fed by a slog tee handler, so it must never call slog itself; every entry passes through `internal/redact` before it is stored (ADR-0070)
- `internal/redact` — masks secrets out of published text: values of secret-keyed env entries the run resolved, plus URL credentials. Applied in `Deployer.emit` (event error + diffs) and the logbuf ring; the console keeps the full text
- `internal/prettylog` — the `pretty` console `log_format` handler (ADR-0042)
- `internal/fsatomic` — atomic file writes (temp file + rename, file and directory fsync) for every persisted file
- `internal/safego` — goroutines that recover from a panic instead of crashing the process
- `internal/uitheme` — UI theme names and palette constants, a leaf package shared by `config` and `ui`
- `internal/ui` — the web UI is **self-contained** (ADR-0035): everything ships inside the binary and is served same-origin — no build step, no bundler, no external/CDN/npm dep, works offline. The app shell markup is the embedded file `static/index.html`; the stylesheet is `static/app.css` and the app is a set of plain-script `static/app-*.js` files, all loaded from `index.html` in the fixed order of the one `appScripts` table in `static.go` — which also drives the `<script>` tags, the service-worker shell and the routes (`ScriptHandler(name)`); a new view file is one line there (ADR-0035 amendments); the pure, DOM-free helpers are `static/app-helpers.js` (loaded first, exposed as globals) and the pure HTML-string renderers `static/app-render.js` (loaded second) so a `node --test` unit layer can import them (`make ui-unit`, its own CI job); the app itself is cut **by view, not by kind** (ADR-0035 amendment), sharing state through the one `App` namespace object `static/app-state.js` defines (loaded third: `App.state` holds every SSE snapshot the views read, `App.resolve` the per-host resolvers over it) — a view file (`app-chrome.js`, `app-panels.js`, `app-detail.js`, `app-hosts.js`, `app-roster.js`, `app-deploys.js`, `app-autosync.js`, `app-logs.js`, `app-clog.js`) attaches its API as `App.<view>` and never touches another file's variables, and `static/app-stream.js` (loaded last) is the SSE dispatcher that writes the store plus the bootstrap, the one ordered sequence of `init()` calls that starts the app; the same plain-script JS is formatted/linted by dev-only Prettier/ESLint devDependencies scoped to `internal/ui/static` (`make ui-fmt` / `make ui-lint`, never shipped in the binary) — `app.css` and `index.html` are excluded, keeping their hand-tuned style; fonts (`static/fonts`) and PWA icons (`static/icons`) are separate embedded files, each served by its own scoped handler. Every main-port response carries a strict CSP (`headers.go`, ADR-0067): no inline `<script>`, `on*=` handler or `eval` — the pre-paint theme script is the file `static/app-prepaint.js`; the UI routes (not `/webhook`/`/healthz`) are also behind the optional `allowed_hosts` Host check (`hostcheck.go`). Read `internal/ui/UI_SPEC.md` before UI changes

## Invariants — do not break these

1. Change detection and the compose file always come from the repo clone (`<stacks_base_dir>/<name>/docker-compose.yml`). `stacks_base_dir` is a path **relative to `repo_dir`** (the clone) — `Load` resolves it to an absolute path once (empty = repo root; absolute or `../`-escaping is rejected), so every downstream consumer joins the resolved value verbatim. `project_directory` (`Stack.ProjectDirectory`, renamed from `working_dir` — see ADR-0045) only sets `--project-directory` (compose project identity + `.env` loading) — never conflate the two. Compose resolves *every* relative path against that directory, `build:` contexts included, so the apply layers on a generated override (`withClonedBuildContexts`, buildcontext.go) pinning each relative context to its absolute path in the clone — otherwise skipper hashes one Dockerfile and builds another, and a base-image bump deploys as a silent no-op (ADR-0057). It is generated once and carried by **every** compose call of that apply, `up` included: a service with `pull_policy: build` builds again inside `up`, and an unpinned second build re-tags the stale image over the pinned one. The rollback is the exception and drops it (the override describes the current compose file, not the restored one). An absolute `context:` and a stack with no `project_directory` are left alone. When a stack sets no `project_directory`, it defaults to `<project_directory_base>/<name>` if the host config sets `project_directory_base` (ADR-0045) — a separate base dir from `stacks_base_dir`, since the two rarely coincide (e.g. a NixOS modules dir vs. the deploy repo clone). Bind mounts are the half that must *not* be pinned to the clone — runtime data belongs in the project directory — so the opt-in `project_directory_sync` (ADR-0060) fast-forwards that checkout once per run, before the stack phase, through `git.Checkout.FastForward`: `merge --ff-only` onto a verified-ancestor commit, refusing on a dirty tree (tracked files only), a missing upstream or a diverged history. A refusal never aborts the run — it is reported under the reserved pseudo-stack `_project_dir` once per distinct message (ADR-0055) with the gauge `skipper_project_dir_sync_error` standing, and a successful fast-forward emits nothing (nor is a refusal counted as a failed deploy in the run tally). A **global** autosync pause skips the phase entirely: unlike skipper's own clone, this tree is mounted by running containers. Host policy, never in `ConfigHash`.
2. Hashed inputs per stack: compose file, `env_files`, global `vars_file`, `watch_dirs` contents (recursive), and Dockerfiles of `build:` services. In stack-discovery mode (ADR-0034) additionally the stack's deploy-shaping config (`Stack.ConfigHash`, keyed by the `skipper.yaml` path at `stacks_base_dir`) — but never `icon`/`self_heal`/`depends_on`/`hooks`/`rollout`, whose edits must not redeploy. A missing/corrupt `state.yaml` means all stacks redeploy — by design, not a bug. Such a **bootstrap run** (state *entirely* empty — evaluated before the nixos phase, which writes `_nixos` hashes first) still converges every stack but deliberately skips `pull` and drops `build --pull`, so no floating tag moves unattended (ADR-0051); `up` stays idempotent and compose still fetches an image the host does not have, so a fresh install is unaffected. Not configurable — no key, no operator judgement.
3. Rollback fetches the old compose file from the stack's own base commit (`state.baseCommitFor`: the HEAD of the last run that settled it, which a failed deploy never advances — ADR-0061) into a temp file; `--project-directory` must then point at the original compose dir (the temp file lives in /tmp). A successful rollback still returns an error wrapping `deploy.ErrRolledBack` — `errors.Is` on it drives the `rolled_back` event status in deploy.go. An optional per-stack `deploy_health_check` (`Stack.DeployHealthCheck`, renamed from `health_check` — see ADR-0047) gates the deploy through the same path: after a plain `up`, skipper's own readiness wait (`awaitReady`, readiness.go) polls `compose ps` on the injected clock, and an optional HTTP probe must answer 2xx within the timeout (ADR-0022). Only a *decided* failure (unhealthy, exited or restarting after a non-zero exit) rolls back; a budget that runs out while a container is still starting (`errStillStarting`) is `failed` and held, never rolled back (ADR-0072). The budget is derived from the slowest compose healthcheck (`start_period + (retries+1)·interval + timeout`, at least 60s) unless `timeout_seconds` is set; an omitted timeout still hashes as 60 in `ConfigHash`. A stack with no `deploy_health_check` set but a compose `healthcheck:` on at least one service gets this gate automatically, at the derived budget with no URL probe — resolved once in `prepareStackRun` (`resolveHealthCheck`, ADR-0046) and stored on `run.stack.DeployHealthCheck`, so rollback.go/rollout.go inherit it without knowing it was inferred; explicit config always wins and `stack.DeployHealthCheck` (unresolved) still feeds `ConfigHash`, not `run.stack.DeployHealthCheck`. A stack with `on_demand_containers` is never auto-gated even if its compose has a `healthcheck:` — `resolveHealthCheck` suppresses it (skipper stops those containers right after `up`, so waiting on them is wrong), unless an explicit `deploy_health_check` opts in (ADR-0049). `deploy_health_check` also accepts a boolean scalar (ADR-0049): `false` (`HealthCheck.Enabled=false`, `IsDisabled()`) explicitly suppresses the gate — for a monitoring-only compose `healthcheck:` on a non-on-demand stack — and `true` enables it at defaults (== `{}`); `resolveHealthCheck` returns nil for a disabled gate. With `deploy_health_check` effective (explicit or inferred), the rollback reruns the same gate (readiness wait + probe); if the restored version also fails it, the error wraps `deploy.ErrRollbackUnhealthy` → `rolled_back_unhealthy` event status — but on a *decided* failure skipper first rolls forward once (`rollForward`: the new version with the full gate), and a passing roll-forward is a plain success (ADR-0072). No roll-forward after an undecided rollback or with `rollback: false`. Without an effective `deploy_health_check`, neither `up` waits. Rollback is opt-out (ADR-0050): `rollback: false` per stack (or globally, per-stack `true` wins; resolved by `Config.RollbackPolicyFor`/`EffectiveRollback`, default on) makes every git-restore path skip the restore — `rollBackFailedDeploy` returns the plain error → `failed` event, the failed containers are left running, and the change is held like any other failure after start (Invariant 9). A third value, `rollback: patch_only` (ADR-0074), skips the restore the same way unless every service's step from `state.Images` to the compose file's images is at most a patch bump or a pinned-digest move under the same version tag (`internal/imageref.Compare`; unclassifiable, added/removed and `build:` services count as too far, the largest step decides), and the error names the step. Resolved once in `deployStacksGated` onto `stack.Rollback` (a `*config.RollbackPolicy`, global default in scope there); `nil` means always. Like `self_heal`/`autosync`, `rollback` is a runtime policy and is **not** in `ConfigHash` — toggling it must not redeploy.
4. NixOS rebuild runs before stack deploys; if it fails, all stack deploys abort — except a switch that activated but left units failed (exit status 4, `nixos.ErrActivatedUnitsFailed`): hashes stay recorded, `_nixos` failed is emitted and the stack phase continues (ADR-0071). Whether a rebuild is due depends on `nixos_rebuild.change_detection`: `derivation` (the default) compares the system derivation stored under the reserved key `nixos.SystemDrvKey` (`@system-drv`), `files` compares the nix file hashes — `DiffHashes` never reports that key, and a derivation-only change marks the rebuild in flight with that key alone (ADR-0065). A failure to *hash* the nix files or to *evaluate* the derivation counts as a phase failure too: nothing can be said about the host config then, and reading it as "nothing changed" would report `_nixos` skipped and deploy the stacks against a config that never applied. Nix hashes are saved to state *before* the rebuild because the rebuild may restart the skipper service. Nix state uses the reserved stack key `_nixos`. The rebuild runs in a transient systemd unit outside skipper's cgroup, bounded by systemd through `RuntimeMaxSec` = `nixos_rebuild.timeout_seconds` (default 3600; an expiry is an ordinary rebuild failure), and the wait for it is abandoned on shutdown — never run it as a direct child or block shutdown on it (ADR-0014). When the rebuild fails *while skipper is still alive* (not a shutdown/self-restart), the pre-saved `_nixos` hashes are reverted so the next sync retries — otherwise a never-applied rebuild is silently marked done (ADR-0015). A rebuild whose switch *self-restarts* skipper (shutdown requested) is NOT a failure: it must not emit a `_nixos` failed event or count an error — instead an in-flight marker (`state.NixOSRebuildInFlight`) is left set and the next startup reconciles it into a `_nixos` success (the rebuild applied in its transient unit), so the UI never shows a stale failure (ADR-0025).
5. `compose pull` is skipped entirely when no `image:` reference changed — and on a bootstrap run, where nothing is recorded so everything would read as changed (Invariant 2, ADR-0051); otherwise it excludes `build:` services and services whose `image:` matches a locally-built image name. The pull decision reads `state.Images` — the compose file's *desired* references — and only that; the separate `state.RunningImages` (what the containers actually ran — read after a successful deploy by joining `compose ps` and `compose images` on the container name, since compose reports the service only on the first and the image id only on the second; the identity is the running reference plus a short image id *only* when that reference carries no digest) exists solely to report a deploy's version change (ADR-0053) and is neither a hashed input nor a pull input, so a floating tag that moved is reported without ever triggering a deploy.
6. Env precedence (highest wins): `env_files` > `vars_file` > `os.Environ()`.
7. All deploys serialize on one mutex (`SyncAndDeployAll`, TryLock-then-Lock); concurrent webhooks wait — they don't queue duplicates.
8. Stack discovery (`stack_discovery`, ADR-0034 + ADR-0043; **defaults to true** — an omitted key enables discovery, set `false` to list the stacks in the host config yourself): the stack *set* comes from the repo per sync (`config.LoadRepoStacks` — directories under `stacks_base_dir` with a `docker-compose.yml`). Per-stack *overrides* come from the one host config's `stacks:` list (matched by name), passed into `LoadRepoStacks(stacksBaseDir, cfg.Stacks)` — **not** a separate in-repo file; a leftover `<stacks_base_dir>/skipper.yaml` is a file-level error (`_config`) so un-migrated config never silently reverts. The same rule applies inside the host config itself: it decodes with `KnownFields(true)`, so an **unknown key is rejected, never ignored** — a typo or a retired key must fail the load rather than leave skipper running with a setting the operator believes is in effect (ADR-0043 amendment). Retired keys are checked first (`internal/config/keys.go`) so the error names the current key; add a rename there whenever a key is retired. Entry-level errors (bad override, broken compose, invalid rollout, missing env/watch path) fail only the affected stacks and block their dependents. Such an error — and a file-level `_config` one — is a **state, not an event**: it is emitted as a `failed` event once, re-emitted only when its message changes, and otherwise stays silent while the gauge `skipper_stack_config_error{stack}` carries the standing condition (ADR-0055); the dedup memory is in process, so a restart re-announces each standing error once. `depends_on` is validated at discovery against the full set, not at config-load (which sees only the override subset). Out-of-run consumers read the effective set via `Deployer.CurrentStacks()` (`stackViews.effective` in main); `cfg.Stacks` in discovery mode holds the raw overrides, not the effective set. A stack that **leaves** the set is reported once as a `removed` event (ADR-0036 amendment) — measured against the *discovered directories* (`RepoStacks.Discovered`), never the deployable set, since a `disabled: true` or entry-errored stack is paused/broken, not gone. The run then forgets its hashes/images (which is what makes the next run silent) and clears any pending queue entry, but **keeps its `project_dirs` entry** — that is what still classifies the running project as orphaned rather than unmanaged. A run that discovers **zero** stacks reports nothing and drops nothing: that is a broken clone far more often than a deleted fleet. The guard counts only real stacks (never `_nixos`/`_config`) and is discovery-only — with `stack_discovery: false` an emptied `stacks:` list is the operator's call and removes what it no longer names (ADR-0036 amendment 2026-10-20). `removed` is deliberately not notifiable.
9. A change whose new version failed after it started — `up`, a health gate, a `post_deploy` hook, a rollout cutover; every such path tags its error `ErrNewVersionFailed` (via the text-free `errNewVersionMark`), rollback or not — is **held** (ADR-0062): `state.Held[stack]` records a fingerprint of the stack's tracked-file hashes, and while the inputs still match it the run emits a live-only `held` event (never history/audit/notify, like `skipped`) and returns `ErrHeld`, which blocks changed dependents. Only changed inputs, a revert (which first converges the stack with one plain `up -d --remove-orphans` of the recorded version — `--build` without `--pull` for built images, no hooks/pull/gate/rollback — keeping the hold if the `up` fails; ADR-0068), removal, or an operator retry (`Deployer.RequestRetry` via `POST /api/stacks/{stack}/retry`, one attempt, consumed by the next run) release it. A failure *before* any container was touched (`pre_deploy`, `pull`, `build`) is recorded in the same `state.Held` entry with `Attempts` and a `RetryAt` (ADR-0064): the run treats it as held until `RetryAt` (5 min, then 10, measured on the injectable `Config.Now`), and the third consecutive failure of the same fingerprint clears `RetryAt`, which makes it an ordinary hold; `skipper_stack_held` is raised only for a hold without `RetryAt`. A hashing failure has no fingerprint and still retries every tick, and a failure caused by shutdown (`ctx.Err()`) is not counted. Any new path that applies the new version must carry the mark, or a broken change loops again.

## Testing

Table-style tests with `t.TempDir()` and real files on disk; inject `recordingRunner` fakes (implementing `command.Runner`) and assert the exact docker/git argv — never shell out for real. Test files in `internal/deploy` mirror the source files (`hash_test.go`, `images_test.go`, …); shared fakes and helpers live in `internal/deploy/helpers_test.go`.

Three deliberate exceptions run real commands: `internal/command` tests (the process boundary — faking exec there would test nothing), `internal/git/integration_test.go` (real `git` against a local repo, catches argv mistakes the fakes cannot; skips when git is missing), and `internal/containerlogs/streamer_test.go` (real `sh` through `ExecStreamer` — the same process-boundary rationale; skips when sh is missing).

**No non-deterministic timing constraints in tests** (backend and frontend alike). A test must never depend on wall-clock timing that only *probably* holds — arbitrary sleeps, waiting a fixed duration for async work, or polling for an effect that might not land. If a test can only be made to pass by waiting-and-hoping, the fault is in the production code: give it a deterministic seam — expose a settled state, signal completion, or accept an injected clock/synchronisation point — so the test asserts the outcome directly instead of racing it.

**An absence assertion needs a positive signal.** A test claiming "X did *not* happen" (no deploy, no notification, no pull) is guaranteed false-green unless the code emits something that proves the decision point was reached — a recorded call list, a settled state, a counter. Assert against that signal, and prove the test can fail: run it against the unfixed build (or temporarily revert the guard) and see it go red.

**Tests must fail for a wrong result.** Assert the specific error (`errors.Is` or the exact message), never just "an error". No assertion-free subtests, and no test that passes on an empty render or an empty result.

**Walk the degenerate states before committing.** Empty input, default values and filters, the error path, multi-digit numbering (`2.10` vs `2.2`) and ranges: cover each that applies with a test.

**Review discipline.** Apply every review suggestion or state why not — never ignore one. The first commit subject describes the whole branch (it becomes the PR title). A review says Ready only with no open finding, after checking whether the new tests could pass for a wrong result, what the change does in degenerate states, and that the PR title matches the whole diff.

## Engineering principles

Priorities for all work in this repo:

- **Test-first**: a new feature starts with tests that specify its behavior (behavior-revealing names like `TestDeployStack_SkipsWhenUnchanged`), then implement until green. Bug fixes start with a failing test reproducing the bug.
- **Readability first**: small files, doc comments on exported symbols, names that reveal behavior. Readable beats clever.
- **Clear responsibilities & encapsulation**: each package/type owns its data — don't pass raw mutable maps/structs around when a type with methods would hide the representation. Delete dead code instead of keeping it "for later"; unused APIs are complexity.
- **Extensibility**: consumer-side interfaces (like `Runner`, `CommitReader`) instead of concrete coupling; keep packages small with one job.
- **Coverage**: every non-trivial package has tests; check `make test` (its coverage total excludes the npm trees `./...` would count) for regressions when touching a package. A package that implements a safety/correctness invariant (e.g. `internal/fsatomic`'s atomic writes) needs its failure paths tested too, not just the happy path.
- **Go conventions**: gofmt/vet clean, sentinel errors (`errors.Is`) instead of matching error strings, `any` instead of `interface{}`, atomic writes (temp file + rename) for persisted state, no magic strings/numbers (hoist a literal to a named constant once it's repeated across files or compared/switched against), never discard an error that matters with `_ = fn()` — log it at minimum, especially for state-persisting calls.
- **English only**: everything that lands in this repo or on a PR is written in English — docs, ADRs, code comments, UI-facing text, commit messages, PR titles and bodies. This holds even when a feature, decision or bug report is dictated in another language; translate it. (Chat/conversation itself can be in any language — only committed and published artifacts must be English.)
- **Comments are terse**: the non-obvious *what* plus the one *why*. Don't narrate the change, restate the code, or repeat rationale that already lives in an ADR — a `// see ADR-00xx` pointer beats a paragraph. A comment that disappears once the value or branch is extracted into a well-named variable or method should be that name instead.
- **Error messages are actionable**: name the exact key, the bad value, and what to set instead (`stacks_base_dir: "/srv/x" is absolute; give a path relative to repo_dir`), not just what went wrong.
- **Commit messages** follow [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/): `<type>(<optional scope>): <description>`. The allowed types are exactly `feat`, `fix`, `docs`, `chore`, `refactor`, `test`, `ci` — nothing else (in particular never `build:`).

## Workflow

How a change gets from an idea to `main`. These rules exist because several sessions may work this repo in parallel.

- **Never commit or push to `main`.** Every change starts as a branch in **its own git worktree** (`.claude/worktrees/<name>/`) — a shared checkout gets its branch swapped underneath a concurrent session, mixing two features' uncommitted work. Push the branch, open a PR, let CI run.
- **The shell's working directory is the real hazard**, not intent: one `cd` into the main checkout persists for every later command, so a later `git commit && git push` silently lands there. Compare against main with `git -C` / `git show main:<path>` instead of `cd`, and check `git branch --show-current` immediately before any commit or push.
- **Merging is a separate, explicitly-granted step.** "Open a PR", "commit", "push" authorise the branch — never the merge. Green CI is the default stopping point: stop there and wait. Permission to merge one PR never carries to the next.
- **Merge style** (once granted): squash with a hand-written Conventional Commit `--subject`/`--body`, not the auto-generated message. Then delete the worktree and the local branch right away (`git worktree remove …` → `git branch -D …`; `-d` refuses a squash-merged branch), as part of the merge — not a later cleanup round.
- **Self-review every PR**: run the `pr-review` skill (`.claude/skills/pr-review/`) on your own diff after opening it, hunting for real findings rather than rubber-stamping. Fix, push, then post the verdict.
- **One PR carries the whole feature**: implementation + tests + its spec/ADR + its UI surface. Don't merge a spec- or ADR-only PR ahead of the code (a decision documented on `main` with nothing running behind it drifts), and don't defer the UI to a follow-up.
- **New ADR only for a real tradeoff** — an alternative that was considered and rejected, or a non-obvious consequence a future reader needs. A purely additive, mechanical config field is a `docs/user/configuration.md` entry plus a code comment, not an ADR.
- **"Next free" identifiers are a race**: ADR numbers (`docs/dev/adr/NNNN-*.md`) and e2e mask letters (`e2e/ui/tests/uX-*.spec.ts` + its `UXn` test IDs + the `docs/dev/e2e-tests.md` section) can be claimed by two open branches at once. Pick against live state — `git fetch` plus open branches, open PRs, and sibling worktrees — and re-check after merging the base branch in, because a PR that sat open can have its number taken.
- **CI is the source of truth for the heavy layers.** Always verify the cheap ones locally (`go build/vet/test`, the Go-level `make e2e`), then push. The strict MkDocs build belongs to CI — don't run it locally. `make e2e-ui` is worth running locally on a machine with the headroom for it (an Apple-silicon laptop); on a small or shared host, skip it and let the `e2e-ui` job report. Pixel comparisons (`RUN_SNAPSHOTS=1`) still need the pinned container to match CI's rendering.

### UI changes

- Start from a **clickable mockup** built with the app's own tokens (`internal/ui/static/app.css`) when the feature is still a prose idea — the feel of an interaction can't be reviewed from a description.
- The rendered UI gets **eyeballed manually before the e2e test is finalized**, so a layout still in flux doesn't get locked into assertions and snapshots. Implement + update `UI_SPEC.md` → hand over for the manual look → then write the mask.
- **Never assert what the UI renders by reading CSS.** Specificity reasoning misses per-property cascade and pseudo-element budgets. Look at pixels: a committed snapshot PNG, or `make ui-preview`.
- A UI PR **shows its change as rendered screenshots**, not prose. Keep them cheap so the repo doesn't grow: 1x (not 2x), `pngquant`ed (~45 KB), 2–3 images cropped to what changed, hosted on a throwaway `assets/pr-<n>-*` branch that is deleted at merge.

## Don'ts & pointers

- **Scope**: skipper-cd *observes and reports* — it deploys on a git push, and the UI visualizes what happened. It is not a control panel: no manual redeploy button, no force-sync, no editing config through the UI. A feature idea that adds a trigger or an editor is out of scope, not a backlog item. (Autosync is the one gate, and it is on by default everywhere; the UI toggle is deliberately non-persistent.)
- Never edit or search `vendor/` (committed on purpose; the nix flake depends on it).
- `./skipper` at the repo root is a build artifact — ignore it.
- Don't duplicate doc content. README.md is a slim landing page (quickstart, features, condensed "How It Works"); the reference lives in `docs/user/` — `docs/user/configuration.md` (config + stack fields + vars_file + icons), `docs/user/nixos.md` (nixos_rebuild + NixOS module + project_directory), `docs/user/docker.md`, `docs/user/metrics.md`, `docs/user/state.md`. Read the relevant page when touching `internal/deploy` or `internal/config`, and keep it in sync. User docs are **terse reference prose**: an example plus short bullets saying what a field does and what it defaults to. The mechanism and the rejected alternatives belong in the ADR — and user pages never link to or cite ADRs (they are not published); explain the behavior inline instead.
- `docs/user/` is published as a MkDocs Material site to GitHub Pages (`mkdocs.yml`, `docs/user/requirements.txt`, `.github/workflows/docs.yml`). The strict build runs in CI and fails on broken links — don't run `mkdocs build` locally; keep nav and cross-links correct by inspection instead. Nav is hand-written in `mkdocs.yml`. `docs/user/` holds **only** user-facing pages (it is the MkDocs `docs_dir`) — contributor/design docs live in `docs/dev/` (see below) and are **not** published; don't link to them from the user manual. The rare unavoidable cross-repo link out of `docs/user/` (e.g. to `internal/ui/UI_SPEC.md`) must be an absolute GitHub URL, not a `../` path, or strict build breaks. The landing-page screenshots (`docs/user/assets/screenshots/*.png`) are **generated, not committed** — the docs workflow renders them from a seeded instance before `mkdocs build`, so a local strict build needs one `make docs-screenshots` run first (docs/dev/e2e-tests.md §5.1).
- **Binary assets** (ADR-0052): binaries that change often stay out of git history — the docs screenshots are generated (above) and the Playwright visual baselines (`e2e/ui/__screenshots__`) are **Git LFS**-tracked. Write-once binaries (logo, embedded fonts, PWA icons) are committed as normal. `git-lfs` on PATH (`nix develop` has it) is needed to **regenerate** a baseline — `git add` fails without it — and for a pixel-comparing run (`RUN_SNAPSHOTS=1`, the `e2e-ui` CI job); a plain local `make e2e-ui` skips the compares, so pointer files are harmless there.
- Autosync/queue semantics (global + per-stack config toggles, non-persistent UI overrides, the leave-dirty queue + pending registry, `queued` event, `/api/autosync` and `/api/queue`) are specified in [`docs/dev/autosync-spec.md`](docs/dev/autosync-spec.md) and [ADR-0016](docs/dev/adr/0016-autosync-and-queue-via-leave-dirty.md); the UI surface is in [`internal/ui/UI_SPEC.md`](internal/ui/UI_SPEC.md). Read them before touching autosync, the per-stack deploy gate, or the queue.
- **`docs/` has exactly two folders.** `docs/user/` holds user and admin docs (manual, installation, usage, operator configuration); `docs/dev/` holds ADRs, specs, plans, architecture, reviews, mockups and developer runbooks. A new document goes into one of them; when in doubt, `docs/dev/`. No other folders under `docs/`.
- Contributor/design docs live in `docs/dev/` (outside the `docs/user/` MkDocs root, so never published; `docs/dev/README.md` is the index): `docs/dev/adr/` holds Architecture Decision Records (one file per decision — significant design changes need a new ADR; the invariants above are their enforcement summary), plus feature specs (`docs/dev/autosync-spec.md`, `docs/dev/pwa-spec.md`, `docs/dev/service-icons-spec.md`, `docs/dev/stack-roster-spec.md`), the shared UI design language (`docs/dev/ui-design-concept.md` — **one look and feel across every view: reuse the same components + CSS (badges, bound panels, the log panel, tap-tip bubble, status/health tokens) rather than building parallel ones**; a new badge/chip/panel/row control also answers *which existing element could carry this* and *what comes off* — see its "Budget every addition"; also the row/table/expand-panel conventions), and `docs/dev/e2e-tests.md`. These are for people working on skipper-cd, not users.

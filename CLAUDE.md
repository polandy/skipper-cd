# skipper-cd

Lightweight Docker Compose CD tool in Go. Receives Git push webhooks (Gitea/GitHub HMAC), keeps a local clone of the deploy repo, and redeploys only stacks whose tracked files changed (SHA-256 hashes persisted in `state.yaml`). Optionally runs `nixos-rebuild` first when nix files change.

## Commands

- Build: `go build ./...` (binary: `go build -o skipper ./cmd/skipper`)
- Test: `go test ./...` — fast, needs no docker/git; tests inject fake runners
- Verify before finishing any change:
  `go build ./... && go vet ./... && go test ./... && test -z "$(gofmt -l cmd internal)"`
  (the `test -z` wrapper is required — `gofmt -l` exits 0 even when files need formatting; the paths `cmd internal` keep `vendor/` out)
- Lint: `golangci-lint run ./...` (config in `.golangci.yml`; locally via `nix run nixpkgs#golangci-lint -- run ./...`). CI runs it plus `go test -race`.
- Nix: `nix build` / `nix develop`. After dependency changes run `go mod tidy && go mod vendor` — the flake uses `vendorHash = null`, so `vendor/` must stay committed and in sync.

## Packages

- `cmd/skipper` — entrypoint; single `-config` flag (default `/etc/skipper/skipper.yml`)
- `internal/config` — YAML config load and validation. Files are cut **by feature area, not by kind**: a section's shape and the rules that make it usable live together (`stack.go`, `healthcheck.go`, `healthwatch.go`, `notifications.go`, `peers.go`), so adding a field and its validation is one file. `config.go` holds the `Config` struct itself, its effective-value methods, `Load` and the shared defaults; `validate.go` only orchestrates (`collectWarnings`, `validateConfig`). Put a new section in its own file rather than growing these two back. In stack-discovery mode `LoadRepoStacks` also validates each stack against its compose file (parse, rollout eligibility, env/watch existence) every sync
- `internal/compose` — minimal read-only `docker-compose.yml` parser (`File`/`Service` + `PublishesPorts`/`HasHealthcheck`/`HasContainerName`); shared by `deploy` (image/build/rollout) and `config` (discovery validation) so there is one parser
- `internal/deploy` — CORE: run-level orchestration (deploy.go), per-stack apply pipeline (stackrun.go), deploy-event emission + change context + repo-relative paths (events.go), change hashing (hash.go), per-service change attribution for display (attribution.go, ADR-0059), image/pull logic (images.go, wraps `internal/compose`), build contexts pinned to the clone (buildcontext.go), reported version deltas from what the containers actually run (runningimages.go), state persistence (state.go), env files (envfile.go)
- `internal/command` — `Runner` interface over os/exec; tests inject fakes through it
- `internal/containerlogs` — UI-only live `docker compose logs` over SSE (`/api/container-logs`, ADR-0037); own `LogStreamer` seam so the deploy path's `Runner` stays run-to-completion
- `internal/git` — local clone management (clone, reset --hard, diff, file-at-commit); also owns what skipper knows about Git remote URL *forms* — redacting credentials for logs, and deriving the forge browse URL the UI links commit SHAs through (`WebURL`)
- `internal/webhook` — HMAC-verified push handler; responds 202 immediately, deploy runs in a goroutine
- `internal/nixos` — nixos-rebuild; must stay free of docker/state/metrics/events knowledge
- `internal/events` — SSE broadcaster + bounded persisted event history. A terminal outcome that merely repeats a stack's previous one (same status, same error; failure statuses only) collapses into it rather than taking a slot, carrying `repeat_count`/`first_seen`/`supersedes_id` (ADR-0056) — the same rule `internal/audit` applies per stack, so one failure loop can never evict a stack's real history
- `internal/metrics` — Prometheus metrics
- `internal/roster` — builds the Stacks-view inventory (discovered/host stack set + last audit outcome per stack) and owns the `stacks` SSE snapshot that wraps it (`State`/`BuildState`/`RepoRef` in state.go); pure (dev-docs/stack-roster-spec.md)
- `internal/registry` — minimal read-only Registry HTTP API v2 client (tags list + manifest-digest HEAD, docker-config credentials, challenge auth); exists solely for the update check (ADR-0054) and must never pull or push
- `internal/updatecheck` — read-only registry update check (ADR-0054): compares each stack's `running_images` against its registries (conservative same-shape tag matching + moved-digest detection), publishes a runtime-only snapshot that rides the `stacks` SSE state, and — only under the opt-in `update_check.notify: true` (default **false**, the UI is the surface) — fires one deduped notification per newly appearing update (dedup persisted in `update-check.yaml`). Never a deploy input — not hashed, not a pull input, no trigger
- `internal/peers` — multi-host read-data fan-in (ADR-0048, dev-docs/multi-host-spec.md): the primary polls each `peers:` instance's `/api/v1/snapshot` + `/api/v1/audit` (falling back to the legacy `/api/audit` only on 404 from an older peer), tags records by host, and exposes one merged `peers` state its own UI renders. Read-only; touches no deploy/state invariant. Wired in main under `ui_enabled` (`GET /api/peers`, the peer-diff proxy `GET /api/peers/{name}/events/{id}/diffs`, and the peer container-logs SSE proxy `GET /api/peers/{name}/container-logs/{stack}[/{service}]`)
- `internal/ui` — the web UI is **self-contained** (ADR-0035): everything ships inside the binary and is served same-origin — no build step, no bundler, no external/CDN/npm dep, works offline. The app shell markup is the embedded file `static/index.html`; the stylesheet is `static/app.css` and the app is a set of plain-script `static/app-*.js` files, all loaded from `index.html` in a fixed order, each embedded and served by its own handler (ADR-0035 amendments); the pure, DOM-free helpers are `static/app-helpers.js` (loaded first, exposed as globals) and the pure HTML-string renderers `static/app-render.js` (loaded second) so a `node --test` unit layer can import them (`make ui-unit`, its own CI job); the app itself is cut **by view, not by kind** (ADR-0035 amendment), sharing state through the one `App` namespace object `static/app-state.js` defines (loaded third: `App.state` holds every SSE snapshot the views read, `App.resolve` the per-host resolvers over it) — a view file (`app-chrome.js`, `app-panels.js`, `app-hosts.js`, `app-roster.js`, `app-deploys.js`, `app-autosync.js`, `app-logs.js`, `app-clog.js`) attaches its API as `App.<view>` and never touches another file's variables, and `static/app-stream.js` (loaded last) is the SSE dispatcher that writes the store plus the bootstrap, the one ordered sequence of `init()` calls that starts the app; the same plain-script JS is formatted/linted by dev-only Prettier/ESLint devDependencies scoped to `internal/ui/static` (`make ui-fmt` / `make ui-lint`, never shipped in the binary) — `app.css` and `index.html` are excluded, keeping their hand-tuned style; fonts (`static/fonts`) and PWA icons (`static/icons`) are separate embedded files, each served by its own scoped handler. Read `internal/ui/UI_SPEC.md` before UI changes

## Invariants — do not break these

1. Change detection and the compose file always come from the repo clone (`<stacks_base_dir>/<name>/docker-compose.yml`). `stacks_base_dir` is a path **relative to `repo_dir`** (the clone) — `Load` resolves it to an absolute path once (empty = repo root; absolute or `../`-escaping is rejected), so every downstream consumer joins the resolved value verbatim. `project_directory` (`Stack.ProjectDirectory`, renamed from `working_dir` — see ADR-0045) only sets `--project-directory` (compose project identity + `.env` loading) — never conflate the two. Compose resolves *every* relative path against that directory, `build:` contexts included, so the apply layers on a generated override (`withClonedBuildContexts`, buildcontext.go) pinning each relative context to its absolute path in the clone — otherwise skipper hashes one Dockerfile and builds another, and a base-image bump deploys as a silent no-op (ADR-0057). It is generated once and carried by **every** compose call of that apply, `up` included: a service with `pull_policy: build` builds again inside `up`, and an unpinned second build re-tags the stale image over the pinned one. The rollback is the exception and drops it (the override describes the current compose file, not the restored one). An absolute `context:` and a stack with no `project_directory` are left alone. When a stack sets no `project_directory`, it defaults to `<project_directory_base>/<name>` if the host config sets `project_directory_base` (ADR-0045) — a separate base dir from `stacks_base_dir`, since the two rarely coincide (e.g. a NixOS modules dir vs. the deploy repo clone).
2. Hashed inputs per stack: compose file, `env_files`, global `vars_file`, `watch_dirs` contents (recursive), and Dockerfiles of `build:` services. In stack-discovery mode (ADR-0034) additionally the stack's deploy-shaping config (`Stack.ConfigHash`, keyed by the `skipper.yaml` path at `stacks_base_dir`) — but never `icon`/`self_heal`/`depends_on`/`hooks`/`rollout`, whose edits must not redeploy. A missing/corrupt `state.yaml` means all stacks redeploy — by design, not a bug. Such a **bootstrap run** (state *entirely* empty — evaluated before the nixos phase, which writes `_nixos` hashes first) still converges every stack but deliberately skips `pull` and drops `build --pull`, so no floating tag moves unattended (ADR-0051); `up` stays idempotent and compose still fetches an image the host does not have, so a fresh install is unaffected. Not configurable — no key, no operator judgement.
3. Rollback fetches the old compose file from `state.LastDeployedCommit` into a temp file; `--project-directory` must then point at the original compose dir (the temp file lives in /tmp). A successful rollback still returns an error wrapping `deploy.ErrRolledBack` — `errors.Is` on it drives the `rolled_back` event status in deploy.go. An optional per-stack `deploy_health_check` (`Stack.DeployHealthCheck`, renamed from `health_check` — see ADR-0047) gates the deploy through the same path: `up` then runs with `--wait --wait-timeout`, and an optional HTTP probe must answer 2xx within the timeout — either failure triggers the same rollback (ADR-0022). A stack with no `deploy_health_check` set but a compose `healthcheck:` on at least one service gets this gate automatically, at the default timeout with no URL probe — resolved once in `prepareStackRun` (`resolveHealthCheck`, ADR-0046) and stored on `run.stack.DeployHealthCheck`, so rollback.go/rollout.go inherit it without knowing it was inferred; explicit config always wins and `stack.DeployHealthCheck` (unresolved) still feeds `ConfigHash`, not `run.stack.DeployHealthCheck`. A stack with `on_demand_containers` is never auto-gated even if its compose has a `healthcheck:` — `resolveHealthCheck` suppresses it (skipper stops those containers right after `up`, so `--wait` is wrong), unless an explicit `deploy_health_check` opts in (ADR-0049). `deploy_health_check` also accepts a boolean scalar (ADR-0049): `false` (`HealthCheck.Enabled=false`, `IsDisabled()`) explicitly suppresses the gate — for a monitoring-only compose `healthcheck:` on a non-on-demand stack — and `true` enables it at defaults (== `{}`); `resolveHealthCheck` returns nil for a disabled gate. With `deploy_health_check` effective (explicit or inferred), the rollback reruns the same gate (`--wait` + probe); if the restored version also fails it, the error wraps `deploy.ErrRollbackUnhealthy` → `rolled_back_unhealthy` event status. Without an effective `deploy_health_check`, the rollback `up` never uses `--wait`. Rollback is opt-out (ADR-0050): `rollback: false` per stack (or globally, per-stack `true` wins; resolved by `Config.RollbackEnabled`/`EffectiveRollback`, default on) makes every git-restore path skip the restore — `rollBackFailedDeploy` returns the plain error → `failed` event, the failed containers are left running, and the change stays pending. Resolved once in `deployStacksGated` onto `stack.Rollback` (global default in scope there); `nil` means on. Like `self_heal`/`autosync`, `rollback` is a runtime policy and is **not** in `ConfigHash` — toggling it must not redeploy.
4. NixOS rebuild runs before stack deploys; if it fails, all stack deploys abort. A failure to *hash* the nix files counts as a phase failure too: nothing can be said about the host config then, and reading the empty diff as "nothing changed" would report `_nixos` skipped and deploy the stacks against a config that never applied. Nix hashes are saved to state *before* the rebuild because the rebuild may restart the skipper service. Nix state uses the reserved stack key `_nixos`. The rebuild runs in a transient systemd unit outside skipper's cgroup, and the wait for it is abandoned on shutdown — never run it as a direct child or block shutdown on it (ADR-0014). When the rebuild fails *while skipper is still alive* (not a shutdown/self-restart), the pre-saved `_nixos` hashes are reverted so the next sync retries — otherwise a never-applied rebuild is silently marked done (ADR-0015). A rebuild whose switch *self-restarts* skipper (shutdown requested) is NOT a failure: it must not emit a `_nixos` failed event or count an error — instead an in-flight marker (`state.NixOSRebuildInFlight`) is left set and the next startup reconciles it into a `_nixos` success (the rebuild applied in its transient unit), so the UI never shows a stale failure (ADR-0025).
5. `compose pull` is skipped entirely when no `image:` reference changed — and on a bootstrap run, where nothing is recorded so everything would read as changed (Invariant 2, ADR-0051); otherwise it excludes `build:` services and services whose `image:` matches a locally-built image name. The pull decision reads `state.Images` — the compose file's *desired* references — and only that; the separate `state.RunningImages` (what the containers actually ran — read after a successful deploy by joining `compose ps` and `compose images` on the container name, since compose reports the service only on the first and the image id only on the second; the identity is the running reference plus a short image id *only* when that reference carries no digest) exists solely to report a deploy's version change (ADR-0053) and is neither a hashed input nor a pull input, so a floating tag that moved is reported without ever triggering a deploy.
6. Env precedence (highest wins): `env_files` > `vars_file` > `os.Environ()`.
7. All deploys serialize on one mutex (`SyncAndDeployAll`, TryLock-then-Lock); concurrent webhooks wait — they don't queue duplicates.
8. Stack discovery (`stack_discovery`, ADR-0034 + ADR-0043; **defaults to true** — an omitted key enables discovery, set `false` to list the stacks in the host config yourself): the stack *set* comes from the repo per sync (`config.LoadRepoStacks` — directories under `stacks_base_dir` with a `docker-compose.yml`). Per-stack *overrides* come from the one host config's `stacks:` list (matched by name), passed into `LoadRepoStacks(stacksBaseDir, cfg.Stacks)` — **not** a separate in-repo file; a leftover `<stacks_base_dir>/skipper.yaml` is a file-level error (`_config`) so un-migrated config never silently reverts. The same rule applies inside the host config itself: it decodes with `KnownFields(true)`, so an **unknown key is rejected, never ignored** — a typo or a retired key must fail the load rather than leave skipper running with a setting the operator believes is in effect (ADR-0043 amendment). Retired keys are checked first (`internal/config/keys.go`) so the error names the current key; add a rename there whenever a key is retired. Entry-level errors (bad override, broken compose, invalid rollout, missing env/watch path) fail only the affected stacks and block their dependents. Such an error — and a file-level `_config` one — is a **state, not an event**: it is emitted as a `failed` event once, re-emitted only when its message changes, and otherwise stays silent while the gauge `skipper_stack_config_error{stack}` carries the standing condition (ADR-0055); the dedup memory is in process, so a restart re-announces each standing error once. `depends_on` is validated at discovery against the full set, not at config-load (which sees only the override subset). Out-of-run consumers read the effective set via `Deployer.CurrentStacks()` (`stackViews.effective` in main); `cfg.Stacks` in discovery mode holds the raw overrides, not the effective set. A stack that **leaves** the set is reported once as a `removed` event (ADR-0036 amendment) — measured against the *discovered directories* (`RepoStacks.Discovered`), never the deployable set, since a `disabled: true` or entry-errored stack is paused/broken, not gone. The run then forgets its hashes/images (which is what makes the next run silent) and clears any pending queue entry, but **keeps its `project_dirs` entry** — that is what still classifies the running project as orphaned rather than unmanaged. A run that discovers **zero** stacks reports nothing and drops nothing: that is a broken clone far more often than a deleted fleet. `removed` is deliberately not notifiable.

## Testing

Table-style tests with `t.TempDir()` and real files on disk; inject `recordingRunner` fakes (implementing `command.Runner`) and assert the exact docker/git argv — never shell out for real. Test files in `internal/deploy` mirror the source files (`hash_test.go`, `images_test.go`, …); shared fakes and helpers live in `internal/deploy/helpers_test.go`.

Three deliberate exceptions run real commands: `internal/command` tests (the process boundary — faking exec there would test nothing), `internal/git/integration_test.go` (real `git` against a local repo, catches argv mistakes the fakes cannot; skips when git is missing), and `internal/containerlogs/streamer_test.go` (real `sh` through `ExecStreamer` — the same process-boundary rationale; skips when sh is missing).

**No non-deterministic timing constraints in tests** (backend and frontend alike). A test must never depend on wall-clock timing that only *probably* holds — arbitrary sleeps, waiting a fixed duration for async work, or polling for an effect that might not land. If a test can only be made to pass by waiting-and-hoping, the fault is in the production code: give it a deterministic seam — expose a settled state, signal completion, or accept an injected clock/synchronisation point — so the test asserts the outcome directly instead of racing it.

**An absence assertion needs a positive signal.** A test claiming "X did *not* happen" (no deploy, no notification, no pull) is guaranteed false-green unless the code emits something that proves the decision point was reached — a recorded call list, a settled state, a counter. Assert against that signal, and prove the test can fail: run it against the unfixed build (or temporarily revert the guard) and see it go red.

## Engineering principles

Priorities for all work in this repo:

- **Test-first**: a new feature starts with tests that specify its behavior (behavior-revealing names like `TestDeployStack_SkipsWhenUnchanged`), then implement until green. Bug fixes start with a failing test reproducing the bug.
- **Readability first**: small files, doc comments on exported symbols, names that reveal behavior. Readable beats clever.
- **Clear responsibilities & encapsulation**: each package/type owns its data — don't pass raw mutable maps/structs around when a type with methods would hide the representation. Delete dead code instead of keeping it "for later"; unused APIs are complexity.
- **Extensibility**: consumer-side interfaces (like `Runner`, `CommitReader`) instead of concrete coupling; keep packages small with one job.
- **Coverage**: every non-trivial package has tests; check `make test` (its coverage total excludes the npm trees `./...` would count) for regressions when touching a package. A package that implements a safety/correctness invariant (e.g. `internal/fsatomic`'s atomic writes) needs its failure paths tested too, not just the happy path.
- **Go conventions**: gofmt/vet clean, sentinel errors (`errors.Is`) instead of matching error strings, `any` instead of `interface{}`, atomic writes (temp file + rename) for persisted state, no magic strings/numbers (hoist a literal to a named constant once it's repeated across files or compared/switched against), never discard an error that matters with `_ = fn()` — log it at minimum, especially for state-persisting calls.
- **English only**: everything that lands in this repo or on a PR is written in English — docs, ADRs, code comments, UI-facing text, commit messages, PR titles and bodies. This holds even when a feature, decision or bug report is dictated in another language; translate it. (Chat/conversation itself can be in any language — only committed and published artifacts must be English.)
- **Comments are terse**: the non-obvious *what* plus the one *why*. Don't narrate the change, restate the code, or repeat rationale that already lives in an ADR — a `// see ADR-00xx` pointer beats a paragraph. A comment that disappears once the value or branch is extracted into a well-named variable or method should be that name instead.
- **Error messages are actionable**: name the exact key, the bad value, and what to set instead (`stacks_base_dir: "/srv/x" is absolute; give a path relative to repo_dir`), not just what went wrong.
- **Commit messages** follow [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/): `<type>(<optional scope>): <description>`. The allowed types are exactly `feat`, `fix`, `docs`, `chore`, `refactor`, `test`, `ci` — nothing else (in particular never `build:`).

## Workflow

How a change gets from an idea to `main`. These rules exist because several sessions may work this repo in parallel.

- **Never commit or push to `main`.** Every change starts as a branch in **its own git worktree** (`.claude/worktrees/<name>/`) — a shared checkout gets its branch swapped underneath a concurrent session, mixing two features' uncommitted work. Push the branch, open a PR, let CI run.
- **The shell's working directory is the real hazard**, not intent: one `cd` into the main checkout persists for every later command, so a later `git commit && git push` silently lands there. Compare against main with `git -C` / `git show main:<path>` instead of `cd`, and check `git branch --show-current` immediately before any commit or push.
- **Merging is a separate, explicitly-granted step.** "Open a PR", "commit", "push" authorise the branch — never the merge. Green CI is the default stopping point: stop there and wait. Permission to merge one PR never carries to the next.
- **Merge style** (once granted): squash with a hand-written Conventional Commit `--subject`/`--body`, not the auto-generated message. Then delete the worktree and the local branch right away (`git worktree remove …` → `git branch -D …`; `-d` refuses a squash-merged branch), as part of the merge — not a later cleanup round.
- **Self-review every PR**: run the `pr-review` skill (`.claude/skills/pr-review/`) on your own diff after opening it, hunting for real findings rather than rubber-stamping. Fix, push, then post the verdict.
- **One PR carries the whole feature**: implementation + tests + its spec/ADR + its UI surface. Don't merge a spec- or ADR-only PR ahead of the code (a decision documented on `main` with nothing running behind it drifts), and don't defer the UI to a follow-up.
- **New ADR only for a real tradeoff** — an alternative that was considered and rejected, or a non-obvious consequence a future reader needs. A purely additive, mechanical config field is a `docs/configuration.md` entry plus a code comment, not an ADR.
- **"Next free" identifiers are a race**: ADR numbers (`dev-docs/adr/NNNN-*.md`) and e2e mask letters (`e2e/ui/tests/uX-*.spec.ts` + its `UXn` test IDs + the `dev-docs/e2e-tests.md` section) can be claimed by two open branches at once. Pick against live state — `git fetch` plus open branches, open PRs, and sibling worktrees — and re-check after merging the base branch in, because a PR that sat open can have its number taken.
- **CI is the source of truth for the heavy layers.** Always verify the cheap ones locally (`go build/vet/test`, the Go-level `make e2e`), then push. The strict MkDocs build belongs to CI — don't run it locally. `make e2e-ui` is worth running locally on a machine with the headroom for it (an Apple-silicon laptop); on a small or shared host, skip it and let the `e2e-ui` job report. Pixel comparisons (`RUN_SNAPSHOTS=1`) still need the pinned container to match CI's rendering.

### UI changes

- Start from a **clickable mockup** built with the app's own tokens (`internal/ui/static/app.css`) when the feature is still a prose idea — the feel of an interaction can't be reviewed from a description.
- The rendered UI gets **eyeballed manually before the e2e test is finalized**, so a layout still in flux doesn't get locked into assertions and snapshots. Implement + update `UI_SPEC.md` → hand over for the manual look → then write the mask.
- **Never assert what the UI renders by reading CSS.** Specificity reasoning misses per-property cascade and pseudo-element budgets. Look at pixels: a committed snapshot PNG, or `make ui-preview`.
- A UI PR **shows its change as rendered screenshots**, not prose. Keep them cheap so the repo doesn't grow: 1x (not 2x), `pngquant`ed (~45 KB), 2–3 images cropped to what changed, hosted on a throwaway `assets/pr-<n>-*` branch that is deleted at merge.

## Don'ts & pointers

- **Scope**: skipper-cd *observes and reports* — it deploys on a git push, and the UI visualizes what happened. It is not a control panel: no manual redeploy button, no force-sync, no editing config through the UI. A feature idea that adds a trigger or an editor is out of scope, not a backlog item. (Autosync is the one gate, and it is on by default everywhere; the UI toggle is deliberately non-persistent.)
- Never edit or search `vendor/` (committed on purpose; the nix flake depends on it).
- `./skipper` at the repo root is a build artifact — ignore it.
- Don't duplicate doc content. README.md is a slim landing page (quickstart, features, condensed "How It Works"); the reference lives in `docs/` — `docs/configuration.md` (config + stack fields + vars_file + icons), `docs/nixos.md` (nixos_rebuild + NixOS module + project_directory), `docs/docker.md`, `docs/metrics.md`, `docs/state.md`. Read the relevant page when touching `internal/deploy` or `internal/config`, and keep it in sync. User docs are **terse reference prose**: an example plus short bullets saying what a field does and what it defaults to. The mechanism and the rejected alternatives belong in the ADR — and user pages never link to or cite ADRs (they are not published); explain the behavior inline instead.
- `docs/` is published as a MkDocs Material site to GitHub Pages (`mkdocs.yml`, `docs/requirements.txt`, `.github/workflows/docs.yml`). The strict build runs in CI and fails on broken links — don't run `mkdocs build` locally; keep nav and cross-links correct by inspection instead. Nav is hand-written in `mkdocs.yml`. `docs/` holds **only** user-facing pages — contributor/design docs live in `dev-docs/` (see below) and are **not** published; don't link to them from the user manual. The rare unavoidable cross-repo link out of `docs/` (e.g. to `internal/ui/UI_SPEC.md`) must be an absolute GitHub URL, not a `../` path, or strict build breaks. The landing-page screenshots (`docs/assets/screenshots/*.png`) are **generated, not committed** — the docs workflow renders them from a seeded instance before `mkdocs build`, so a local strict build needs one `make docs-screenshots` run first (dev-docs/e2e-tests.md §5.1).
- **Binary assets** (ADR-0052): binaries that change often stay out of git history — the docs screenshots are generated (above) and the Playwright visual baselines (`e2e/ui/__screenshots__`) are **Git LFS**-tracked. Write-once binaries (logo, embedded fonts, PWA icons) are committed as normal. `git-lfs` on PATH (`nix develop` has it) is needed to **regenerate** a baseline — `git add` fails without it — and for a pixel-comparing run (`RUN_SNAPSHOTS=1`, the `e2e-ui` CI job); a plain local `make e2e-ui` skips the compares, so pointer files are harmless there.
- Autosync/queue semantics (global + per-stack config toggles, non-persistent UI overrides, the leave-dirty queue + pending registry, `queued` event, `/api/autosync` and `/api/queue`) are specified in [`dev-docs/autosync-spec.md`](dev-docs/autosync-spec.md) and [ADR-0016](dev-docs/adr/0016-autosync-and-queue-via-leave-dirty.md); the UI surface is in [`internal/ui/UI_SPEC.md`](internal/ui/UI_SPEC.md). Read them before touching autosync, the per-stack deploy gate, or the queue.
- Contributor/design docs live in `dev-docs/` (outside `docs/` so MkDocs never publishes them): `dev-docs/adr/` holds Architecture Decision Records (one file per decision — significant design changes need a new ADR; the invariants above are their enforcement summary), plus feature specs (`dev-docs/autosync-spec.md`, `dev-docs/pwa-spec.md`, `dev-docs/service-icons-spec.md`, `dev-docs/stack-roster-spec.md`), the shared UI design language (`dev-docs/ui-design-concept.md` — **one look and feel across every view: reuse the same components + CSS (badges, bound panels, the log panel, tap-tip bubble, status/health tokens) rather than building parallel ones**; a new badge/chip/panel/row control also answers *which existing element could carry this* and *what comes off* — see its "Budget every addition"; also the row/table/expand-panel conventions), and `dev-docs/e2e-tests.md`. These are for people working on skipper-cd, not users.
